## 0. Главный архитектурный принцип – Thin Client Architecture

ESP32 является **тонким клиентом**.  
Вся бизнес-логика находится в программе на ПК (`GameDesk.exe`).

**ESP32 отвечает только за:**  
- отображение пользовательского интерфейса  
- обработку нажатий кнопок (короткое/долгое нажатие, антидребезг)  
- навигацию между экранами  
- связь с ПК по Serial  

**ESP32 НЕ выполняет:**  
- расчёты статистики  
- анализ игровых процессов  
- сбор телеметрии  
- сортировку, фильтрацию, формирование списков  
- принятие решений об отображении данных  

**GameDesk.exe отвечает за:**  
- сортировку, фильтрацию, ограничение количества элементов  
- подготовку данных для каждого экрана  
- управление игровыми сессиями  
- сбор телеметрии ПК  
- формирование пакетов данных и команд  
- хранение статистики

## 1. Назначение системы

GameDesk — это настольное аппаратно-программное устройство, отображающее в реальном времени:

- активную игру на ПК  
- длительность текущей игровой сессии  
- системные параметры ПК (температура CPU/GPU, использование RAM)  
- игровую статистику (общее время, за неделю, за месяц, дата последнего запуска)  
- список последних игр  

Устройство работает как внешний интерактивный дисплей, подключённый к ПК через USB.

## 2. Архитектура системы

### 2.1 ПК (GameDesk.exe)

ПК является **единственным источником данных** и команд.  
Выполняет:

- определение запущенных игр (process monitoring)  
- управление игровыми сессиями (начало/конец, расчёт времени)  
- сбор системной телеметрии (CPU, GPU, RAM)  
- получение FPS (опционально)  
- логирование событий (запуск/завершение игры, сессии)  
- формирование пакетов данных для ESP32 (включая списки RECENT GAMES)  
- отправку данных на ESP32 через Serial  
- автоматическое обнаружение ESP32 (Handshake)  
- хранение статистики в файле `games.json`

### 2.2 Устройство (ESP32)

ESP32 выполняет:

- приём данных и команд с ПК  
- парсинг пакетов  
- управление интерфейсом (переключение экранов, скролл)  
- отрисовку UI на дисплее (частичное обновление)  
- обработку нажатий 5 кнопок (LEFT, RIGHT, UP, DOWN, CENTER)  
- регулировку яркости (через ШИМ, если поддерживается дисплеем)  
- программный сброс и перезагрузку  
- отладочный режим (DEBUG)

## 3. Аппаратная часть

### 3.1 Микроконтроллер  
- **NodeMCU ESP-32S (38 pin)**, чип ESP32-WROOM  
- USB подключение к ПК  
- питание от USB (5V)  
- стабильная работа 24/7

### 3.2 Дисплей  
- **TFT LCD 2.8"**  
- Контроллер: ST7789V  
- Разрешение: 320×240 (альбомная ориентация)  
- Интерфейс: SPI  
- Цвета: 65K RGB  
- Питание платы дисплея: **5V** (на плате установлен стабилизатор LDO U2 + резисторы R1–R3, который понижает 5V → 3.3V для чипа ST7789V). Подключать VCC дисплея к пину **5V** ESP32.
- Чип тачскрина XPT2046 **не распаян** (посадочное место U1 пустое) — тачскрин недоступен.
- *Примечание:* регулировка яркости возможна только если вывод подсветки (LED) подключён к GPIO ESP32. В противном случае пункт меню Brightness отсутствует или недоступен.

### 3.3 Управление  
Устройство управляется **5 тактовыми кнопками** (momentary push), припаянными к плате или корпусу.

| Кнопка | GPIO | Назначение |
|--------|------|------------|
| LEFT   | GPIO26 | Переключение экрана влево / выход из DETAIL VIEW |
| RIGHT  | GPIO27 | Переключение экрана вправо |
| UP     | GPIO14 | Навигация вверх / скролл вверх |
| DOWN   | GPIO32 | Навигация вниз / скролл вниз |
| CENTER | GPIO13 | Короткое нажатие — контекстное действие; долгое (1.5–2 с) — вход/выход SETTINGS |

**Схема подключения каждой кнопки:** один контакт → GPIO, второй контакт → GND.  
Внутренняя подтяжка ESP32 (INPUT_PULLUP) — внешние резисторы не нужны.  
**Антидребезг:** программный, фильтр 30–50 мс.

## 4. UI архитектура (State Machine)

Интерфейс основан на состояниях:

- `BOOT`  
- `HOME (GAME)`  
- `MONITOR`  
- `STATS`  
- `RECENT GAMES`  
- `DETAIL VIEW`  
- `SETTINGS`

Переходы между экранами:  
- **LEFT / RIGHT** — переключение по кольцу:  
  `HOME ↔ MONITOR ↔ STATS ↔ RECENT GAMES ↔ HOME`  
  *Исключение:* в состоянии `DETAIL VIEW` кнопка **LEFT** не переключает экран, а возвращает в `RECENT GAMES`  
- **CENTER (долгое, 1.5–2 с)** — вход/выход в `SETTINGS` из любого состояния  
- **LEFT** из `DETAIL VIEW` — возврат в `RECENT GAMES`  
- **CENTER (короткое)** в `RECENT GAMES` — открыть `DETAIL VIEW` для выбранной игры

---

## 5. BOOT-последовательность

**Время загрузки:** ≤ 4 секунд

**Этапы:**  
1. Отображение логотипа GameDesk (fade-in)  
2. Анимация загрузки (progress bar)  
3. Инициализация Serial (приём данных)  
4. Переход в `HOME`

**Требования:**  
- прогресс плавный, UI не блокируется  
- инициализация Serial выполняется параллельно анимации  
- **DEBUG MODE:** если при включении удерживать кнопку **CENTER** (≥2 с во время boot-анимации) — активируется вывод отладочных сообщений в USB Serial (RAW-пакеты, ошибки парсинга, состояние кнопок)

## 6. Протокол передачи данных (ПК → ESP32)

### 6.1 Общий формат пакета

Пакет заключается в угловые скобки `<` и `>`.

**Простые пакеты (одиночные):**  
`<VER=1;DEVICE=GAMEDECK;GAME=RDR2;SESSION=01:42:18;STATE=RUNNING;FPS=118;CPU=54;GPU=67;RAM=41>`

**Групповые пакеты для списков (RECENT GAMES):**  
```
<LIST=RECENT;COUNT=3>
<GAME=RDR2;TOTAL=10:23;LAST=2025-03-15;WEEK=02:15;MONTH=08:42>
<GAME=CS2;TOTAL=05:12;LAST=2025-03-14;WEEK=01:30;MONTH=03:44>
<GAME=CIV6;TOTAL=42:01;LAST=2025-03-10;WEEK=00:00;MONTH=12:18>
</LIST>
```

### 6.2 Обязательные поля

Поля `VER` и `DEVICE` **обязательны**:
- в первом пакете, отправляемом после установки соединения (Handshake),
- при изменении версии протокола,
- при восстановлении связи после потери.

В остальных пакетах эти поля могут опускаться для уменьшения объёма данных. Рекомендуется повторять их в каждом пятом пакете для надёжности.

### 6.3 Поля данных

| Поле      | Описание                                    | Значения                                  |
|-----------|---------------------------------------------|-------------------------------------------|
| GAME      | Название активной игры (или `NONE`)         | строка без символов `; < > =`             |
| SESSION   | Время текущей сессии                        | `HH:MM:SS`                                |
| STATE     | Состояние                                   | `RUNNING`, `IDLE`, `OFFLINE`              |
| FPS       | Кадры в секунду                             | число или `-1` (нет данных)               |
| CPU       | Температура CPU (°C)                         | число или `-1`                            |
| GPU       | Температура GPU (°C)                         | число или `-1`                            |
| RAM       | Использование памяти (%)                    | число или `-1`                            |
| HB        | Heartbeat (опционально)                     | `1` (пакет-пульс)                         |
| LIST      | Тип списка                                  | `RECENT`                                  |
| COUNT     | Количество элементов в списке               | число                                     |
| GAME...   | Игровая запись для списка                   | `GAME=...;TOTAL=...;LAST=...;WEEK=...;MONTH=...` |

### 6.4 Handshake (поиск COM-порта)

**Алгоритм GameDesk.exe:**  
1. Перебирает все доступные COM-порты  
2. Отправляет в каждый порт запрос: `<CMD=PING>`  
3. Ожидает ответ в течение 1 секунды  
4. При получении `<CMD=PONG;DEVICE=GAMEDECK;VER=1>` — порт считается найденным, устройство готово к работе  

**Запрещается** хардкодить номер COM-порта.

### 6.5 Отсутствующие данные

Если какой-либо параметр телеметрии недоступен, ПК передаёт `-1`.  
ESP32 отображает это как `--` (прочерк).  
Пример: `FPS=-1;CPU=-1;GPU=-1;RAM=-1`

### 6.6 Heartbeat (не фиксируется жёстко)

Рекомендуемая, но не обязательная реализация:  
- Когда игра активна (`STATE=RUNNING`) – данные и так приходят часто (раз в 1–2 секунды).  
- Когда игра не активна (`STATE=IDLE`) – ПК может отправлять упрощённый пакет `<STATE=IDLE;HB=1>` раз в 1–2 секунды.  
- Отсутствие любых пакетов >5 секунд интерпретируется как потеря связи (`OFFLINE`).

### 6.7 Требования к парсингу на ESP32

- Неполные или повреждённые пакеты игнорируются  
- Данные обновляются только при получении корректного пакета  
- Групповые пакеты `<LIST>...</LIST>` накапливаются в буфере до закрывающего тега, затем парсятся и отображаются  
- ESP32 не выполняет сортировку или фильтрацию полученных данных – только отображение

### 6.8 Технические ограничения протокола
- **максимальная длина DATA-пакета:** 256 байт  
- **максимальная длина LIST-пакета:** 512 байт (при необходимости – авто-фрагментация с `PART=1/2`)  
- **При фрагментации:** если `</LIST>` не получен в течение 500 мс после последнего байта – весь пакет отбрасывается, частичные списки не отображаются  
- рекомендуемая частота обновления: 1–5 Гц (жёсткий лимит 10 Гц)  
- принимаются только полные пакеты  
- групповые пакеты буферизируются до закрывающего `</LIST>`

---

## 7. Поведение при потере соединения

- Если пакеты не поступают более 5 секунд → `STATE = OFFLINE`  
- Экран показывает сообщение **PC OFFLINE** (на чёрном фоне, без мерцания)  
- При восстановлении получения пакетов – автоматический возврат в нормальный режим (последний активный экран)  
- Перезагрузка устройства не требуется

## 8. UI экраны

### 8.1 HOME (GAME)

Отображает:  
- название текущей игры  
- таймер сессии (HH:MM:SS)  
- статус (`RUNNING` / `IDLE` / `OFFLINE`)  

Пример:
```
RDR2
01:42:18
RUNNING
```

### 8.2 MONITOR

Отображает в реальном времени:  
- FPS (или `--`)  
- CPU температура (или `--`)  
- GPU температура (или `--`)  
- RAM использование (или `--`)

### 8.3 STATS

Отображает накопленную статистику (данные приходят от ПК в отдельных пакетах или в составе пакета `HOME`):  
- игровое время за неделю  
- игровое время за месяц  
- общее количество запускавшихся игр

### 8.4 RECENT GAMES

Список последних игр (максимум 10), отсортированный по дате последнего запуска (убывание).  
Каждая строка содержит:  
- название игры  
- общее время игры  

Если игр нет — отображается сообщение **«Нет данных»**.  
Если игр меньше, чем помещается на экран (например, 2–3), отображаются все без пустых строк.

**Навигация:**  
- **UP / DOWN** – перемещение по списку (активный пункт подсвечивается)  
- Если элементов больше видимой области – список прокручивается  
- **CENTER (короткое)** – открыть `DETAIL VIEW` для выбранной игры
- **LEFT / RIGHT** – переключение экранов по кольцу (как на других экранах)

### 8.5 DETAIL VIEW

Открывается из `RECENT GAMES` по короткому нажатию **CENTER** (кнопка CENTER, <500 мс).  
Отображает по выбранной игре:  
- название игры  
- общее время игры (total)  
- время за неделю (weekly)  
- время за месяц (monthly)  
- дату последнего запуска (YYYY-MM-DD)

**Выход:**  
- **LEFT** – вернуться к списку `RECENT GAMES`  
- **CENTER (долгое, 1.5–2 с)** – выход в `SETTINGS` (глобально)

### 8.6 SETTINGS

**Вход:** долгое нажатие **CENTER** (1.5–2 секунды) из любого состояния, кроме самого меню SETTINGS.  
**Выход:** повторное долгое нажатие CENTER или выбор пункта `Exit` (короткое CENTER).

**Пункты меню (v1.0):**

1. **Connection Status** (диагностика)  
   Показывает:  
   ```
   Device: Connected
   Protocol: v1
   Last packet: 1 sec ago
   Heartbeat: OK
   ```

2. **About**  
   ```
   GameDesk
   FW: 1.0
   ESP32-32S NodeMCU
   ST7789V
   ```

3. **Restart Device**  
   Программная перезагрузка ESP32.

4. **Exit**  
   Выход из меню SETTINGS.

**Что НЕ входит в v1.0 (перенесено в v1.1):**
- Brightness (регулировка яркости дисплея)
- Display Settings (анимации, загрузочный логотип)
- Reset Device (сброс локальных настроек ESP32)

**Что НЕ входит в SETTINGS (остаётся на стороне ПК):**  
- сброс статистики  
- управление списком игр  
- сортировка  
- настройки телеметрии

## 9. Управление кнопками (полная спецификация)

**Тип:** 5 тактовых кнопок (momentary push), подключение к GND, INPUT_PULLUP на ESP32.

| Кнопка | GPIO | Короткое нажатие (<500 мс) | Долгое нажатие (≥1500 мс) |
|--------|------|---------------------------|--------------------------|
| **LEFT** | GPIO26 | Экран влево (по кольцу); из DETAIL VIEW → RECENT GAMES | — |
| **RIGHT** | GPIO27 | Экран вправо (по кольцу) | — |
| **UP** | GPIO14 | Навигация вверх / скролл вверх | — |
| **DOWN** | GPIO32 | Навигация вниз / скролл вниз | — |
| **CENTER** | GPIO13 | Контекстное действие (RECENT GAMES → открыть DETAIL VIEW; SETTINGS → выбрать пункт) | Вход/выход в SETTINGS из любого состояния |

**Поведение LEFT/RIGHT в состоянии SETTINGS:**  
В режиме SETTINGS кнопки LEFT и RIGHT **заблокированы** — не переключают экраны.  
Активны только UP/DOWN (навигация по пунктам) и CENTER (выбор/выход).  
Это предотвращает случайный выход из настроек при промахе.

**Требования к обработке:**  
- антидребезг: программный фильтр 30–50 мс  
- долгое нажатие CENTER не должно вызывать короткое действие  
- отклик кнопок менее 100 мс  
- опрос кнопок в каждой итерации loop() (non-blocking, через millis())

## 10. Обновление экрана

**Запрещено:**  
- полная очистка экрана при каждом обновлении  
- мерцание, заметное глазу  

**Требуется:**  
- частичное обновление областей (только изменённые значения)  
- для таймера сессии – обновление посекундно (либо по новым данным от ПК, если частота ≤1с)  
- для списков – перерисовка только изменённой строки или полный рендер списка без мерцания (двойная буферизация при необходимости)

## 11. Программа GameDesk.exe (ПК)

**Функции:**  
- обнаружение активных игр (мониторинг процессов)  
- управление игровыми сессиями (старт/стоп, учёт времени)  
- сбор телеметрии ПК (LibreHardwareMonitor / OpenHardwareMonitor)  
- логирование событий (запуск/завершение игры, подключение устройства)  
- формирование пакетов данных (одиночных и групповых)  
- отправка данных на ESP32 через Serial (автоматическое обнаружение порта по Handshake)  
- хранение статистики в `games.json` (структура: игра → total_time, weekly_time, monthly_time, last_played)  
- **сортировка и фильтрация для списка RECENT GAMES** (по дате последнего запуска, ограничение количества)  
- опционально: получение FPS через RTSS или PresentMon

**Требования:**  
- запрещено хардкодить COM-порт  
- запрещено передавать на ESP32 необработанные списки – только готовые к отображению данные  
- при запуске игра, не входящая в список RECENT GAMES, должна добавиться в него (и в статистику)  
- при запросе DETAIL VIEW (по команде от ESP32? в v1.0 не требуется, т.к. DETAIL VIEW получает данные из того же группового пакета) – в v1.0 все данные для DETAIL VIEW передаются внутри пакета LIST при открытии экрана.

*Примечание:* в v1.0 ESP32 не отправляет команды на ПК (кроме неявного Handshake). Все данные для DETAIL VIEW загружаются один раз при входе в RECENT GAMES. Если требуется актуальная статистика при открытии DETAIL VIEW – ПК должен периодически обновлять список RECENT GAMES, даже если экран не активен.

## 12. Статистика (хранение на ПК)

**Файл:** `games.json`  

**Данные на каждую игру:**  
- `total_time` (секунды)  
- `weekly_time` (секунды, сбрасывается раз в неделю)  
- `monthly_time` (секунды, сбрасывается раз в месяц)  
- `last_played` (timestamp ISO 8601)  
- `session_count` (количество сессий) – опционально  

**Обновление:** при завершении игровой сессии.

**Передача на ESP32:**  
- для экрана `STATS` – общая статистика (weekly, monthly, total games)  
- для списка `RECENT GAMES` – для каждой игры: название, total_time, last_played, weekly_time, monthly_time

## 13. Телеметрия ПК

**Источники:**  
- LibreHardwareMonitor (рекомендуется)  
- OpenHardwareMonitor  

**Параметры:**  
- CPU temperature (°C)  
- GPU temperature (°C)  
- RAM usage (%)  

При недоступности любого параметра передаётся `-1`.

## 14. FPS (опционально для v1.0)

**Источники (приоритет):**  
1. RTSS (RivaTuner Statistics Server)  
2. PresentMon  

Если FPS недоступен – передаётся `-1`.  
FPS не является обязательным для версии 1.0.

## 15. Отладочный режим (DEBUG MODE)

**Активация:** удержание кнопки **CENTER** (≥2 с) во время BOOT-анимации (до завершения progress bar).  

**Что происходит:**  
- ESP32 начинает выводить в USB Serial (на ПК) отладочную информацию:  
  - полученные сырые пакеты  
  - результаты парсинга (OK/ERR)  
  - ошибки: «неизвестное поле», «незакрытый тег», «длина превышена»  
  - состояние кнопок (нажатия, тайминги, антидребезг)  
  - переключения состояний  
  - информацию о производительности (время отрисовки, FPS дисплея)  

**Отключение:** перезагрузка устройства (аппаратно или через меню Restart Device).  
Режим не влияет на основную работу, но может незначительно снизить производительность – только для отладки.

## 16. Нефункциональные требования

- стабильная работа 24+ часов без зависаний  
- автоматическое восстановление соединения после потери связи  
- минимальное мерцание UI (частичное обновление)  
- отклик кнопок <100 мс  
- корректная работа при отключении ПК (показ OFFLINE)  
- плавная работа анимаций без блокировки цикла опроса кнопок

## 17. Критерии готовности v1.0

Система считается готовой к выпуску, если:

- [x] ESP32 загружается ≤4 секунд, показывает логотип и прогресс  
- [x] ПК находит устройство через Handshake (PING/PONG)  
- [x] Определяется активная игра, отображается таймер сессии  
- [x] Работает переключение между экранами `HOME`, `MONITOR`, `STATS`, `RECENT GAMES`  
- [x] `RECENT GAMES` показывает список последних игр с прокруткой  
- [x] Короткое нажатие CENTER на игре в `RECENT GAMES` открывает `DETAIL VIEW` с корректной статистикой  
- [x] Мониторинг CPU/GPU/RAM работает (или показывает `--` при недоступности)  
- [x] Протокол Serial корректен (одиночные и групповые пакеты)  
- [x] Режим `OFFLINE` срабатывает при отключении ПК и восстанавливается автоматически  
- [x] Меню `SETTINGS` полностью функционально (Connection Status, Restart Device, About)  
- [x] Отладочный режим (`DEBUG`) выводит информацию в Serial  
- [x] Нет критических зависаний (тест 24 часа)

## 19. Принцип разработки

**WORKING → STABLE → BEAUTIFUL → SMART**

- **WORKING** – сначала базовая функциональность (определение игры, вывод таймера, переключение экранов)  
- **STABLE** – отказоустойчивость, авто-восстановление, отсутствие зависаний  
- **BEAUTIFUL** – плавные анимации, продуманный UI, читаемые шрифты  
- **SMART** – дополнительные "умные" функции (прогноз времени, рекомендации игр и т.п.)  

**Запрещено нарушать порядок развития системы.**  
v1.0 = WORKING + STABLE. Остальное – в следующих версиях.
